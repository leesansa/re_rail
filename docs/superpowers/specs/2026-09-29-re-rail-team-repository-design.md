# re_rail 4인 협업 저장소 설계

## 목적과 범위

기존 공개 저장소 `leesansa/re_rail`을 네 사람이 HTML, CSS, JavaScript 웹 프로젝트를 함께 개발할 수 있는 상태로 정비한다. 저장소 소유자는 `leesansa`로 유지하고, `main`을 기본 브랜치로 사용한다. 이 작업은 협업 권한, 작업 규칙, 기본 저장소 파일을 다룬다. 제품 기능과 배포는 범위에 포함하지 않는다.

## 현재 상태

- 공개 저장소이며 `main`에 README 제목만 있다.
- 협업자, 브랜치 보호 규칙, 규칙 모음이 없다.
- 로컬 작업 폴더는 비어 있다.

## 접근 권한

`yeadm`, `cool-333`, `soonbub99`를 협업자로 초대한다. 초대 수락 후 소유자를 포함해 네 사람이 작업한다. 개인 계정 저장소이므로 세부 역할을 나누는 조직 권한 체계는 사용하지 않는다. 저장소는 공개 상태를 유지한다.

## 작업 흐름

작업마다 GitHub 이슈를 만들거나 기존 이슈를 선택한다. 각 개발자는 `main`에서 짧은 작업 브랜치를 만들고, 변경 사항을 PR로 제안한다. PR에는 변경 내용, 관련 이슈, 확인 방법을 적고 다른 팀원 한 명의 승인을 받은 뒤 병합한다. 병합은 squash 방식을 기본으로 사용하며 병합된 브랜치는 자동 삭제한다.

`main` 규칙 모음은 PR과 승인 리뷰 1개를 요구하고 강제 푸시와 브랜치 삭제를 금지한다. 소유자에게도 예외를 주지 않는다. 필수 상태 검사는 실제 검사 도구와 명령이 정해진 후 추가한다. 규칙 적용 전 기본 파일을 먼저 넣어 빈 저장소에서 리뷰 요구 때문에 초기 구성이 막히지 않게 한다. 규칙 적용 후에는 초대받은 팀원 한 명이 수락해야 다음 PR을 병합할 수 있다.

## 저장소 파일

- `README.md`: 프로젝트명, 기술 스택, 저장소 구조와 실행 방법을 현재 사실에 맞게 안내한다. 웹 페이지 파일이 생기기 전에는 존재하지 않는 실행 명령을 적지 않는다.
- `CONTRIBUTING.md`: 이슈, 브랜치, PR, 리뷰, 병합 절차와 비밀값을 커밋하지 않는 규칙을 적는다.
- `.github/PULL_REQUEST_TEMPLATE.md`: 변경 요약, 관련 이슈, 확인 결과를 작성하도록 한다.
- `.github/ISSUE_TEMPLATE/`: 기능 작업과 오류 보고용 양식을 둔다.
- `.gitignore`: 운영체제·편집기 임시 파일, 로컬 환경 변수 파일을 제외한다.
- `.editorconfig`: UTF-8, 줄바꿈, 기본 들여쓰기 규칙을 통일한다.

라이선스는 공개 여부와 별개의 권리 결정이므로 추가하지 않는다. 프레임워크와 패키지 관리자는 사용하지 않는다.

## 확인 기준

저장소가 공개 상태이고 협업자 3명에게 초대가 전달되어야 한다. 위 파일이 `main`에 보이고, 규칙 모음에 PR·승인 1개·강제 푸시 및 삭제 금지가 표시되어야 한다. 일반 설정에는 squash 병합과 병합 후 브랜치 자동 삭제가 적용되어야 한다. 초대 수락 여부는 별도로 확인한다.
